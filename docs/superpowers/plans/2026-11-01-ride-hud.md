# Ride HUD ("Refined" look) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the in-ride dashboard with the new HUD (left time/distance panel, centre panel with power + heart-rate zone gauges and a speed/slope/cadence/gear row, top-right workout panel), with zone data and a max-HR setting coming from services.

**Architecture:** `incyclist-services` adds a `gauge` description (scale, zones, current zone, workout target) to the Power and Heartrate dashboard items, a `gearCount` to the Gear item, and a `user.maxHr` setting. web-ui maps the existing `getDashboardDisplayProperties()` items to a small view model, renders it with new pure views (`ZoneGauge`, `MetricValue`, `GearValue`) inside two smart panels, and positions every ride overlay from one shared, unit-tested layout function instead of per-page literals.

**Tech Stack:** services: TypeScript, jest. web-ui: React 19, styled-components 6, vitest + @testing-library/react, Storybook.

**Spec:** `web-ui/docs/superpowers/specs/2026-11-01-modern-look-design.md` (+ images in `2026-11-01-modern-look/`). This plan covers the ride screen, the shared tokens it needs and the ride-related bug fixes. Base controls, Devices and Route details get a second plan.

**One refinement of the spec:** decision 18 says to expose the gear count from `devices`. The cycling mode already publishes it: the `startGear` property has `max: 24` and only applies when `virtshift` is `Incyclist` or `SmartTrainer` (`devices/src/modes/antble-smarttrainer.ts:135`). Services reads that, so the `devices` repo is not touched.

- web-ui: follow `web-ui/docs/CODEBASE_GUIDE.md` — atoms/molecules/modules, barrel imports, relative imports, styled-components, `vw`/`vh` units, smart `<Name>` + pure `<Name>View` for new components (barrel exports only the smart half), stories `*.stories.jsx`, tests `*.unit.test.jsx` colocated.

- services: 4-space indent, single quotes, no semicolons, types only in `types.ts`, JSDoc on exported functions, `@Injectable` on service getters; re-read the diff against the SonarQube list in `services/CLAUDE.md`. Tests: `cd services && npx jest <file>`; full: `npm test`. Never bare `npx jest`. `npm run lint` before committing.
- Accent `#e4a13c` (text on accent `#1c1203`); success green `#8dc100`; panel gradient `rgb(56,1,31) → rgb(26,4,86)` at ≈0.72 opacity over video.
- No small secondary text on the ride screen: no avg/max lines, no "ridden"/"to go" captions.
- Labels are icons (clock, flag, speedometer, bolt, heart, gradient triangle, rotation arrow, cog).
- Remaining values use a real minus sign `−` (U+2212), dimmed, right-aligned.
- Gauges: 240° arc, "needle on zones", medium size, zone name shown in the zone's colour.
- Power zones (Coggan, % FTP, upper bounds inclusive): Z1 Recovery ≤55, Z2 Endurance ≤75, Z3 Tempo ≤90, Z4 Threshold ≤105, Z5 VO2max ≤120, Z6 Anaerobic ≤150, Z7 Sprint >150; power gauge range 0–160 % FTP.
- HR zones (% max HR): Z1 <60, Z2 60–70, Z3 70–80, Z4 80–90, Z5 ≥90; gauge range 50–100 % max HR.
- Zone colours: `WORKOUT_ZONE_COLORS[1..7]` from `services/src/workouts/base/graph/series.ts`.
- Controller navigation keeps working: interactive HUD elements stay real buttons (`WorkoutButton`/`Button`) so `modules/ControllerNavigation` finds them.

## Review Focus

1. **No sensor value yet** (HR strap off, before pedalling: services sends `''`) → value shows `–`, gauge draws no needle, nothing throws. Pinned in Task 8 and Task 10.
2. **Values outside the gauge range** (500 W sprint above 160 % FTP, HR above max, negative slope) → needle clamps to the arc end, the number shows the real value. Pinned in Task 10.
3. **FTP or max HR not set** → the gauge shows a neutral grey arc with a needle, no zones, no zone name; power scale 0–400 W, HR 40–200 bpm. Pinned in Task 3 and Task 10.
4. **Imperial units and non-cycling sports** (mi, mph, rowing pace `2:05` with empty unit, `spm`) → numbers and units pass through unchanged; distance remaining keeps its unit. Pinned in Task 8.
5. **Every overlay on at once** (workout + upcoming elevation + nearby riders + previous rides + both Street View slots + map + elevation) → no two visible regions overlap and none covers the band 40–75 vh in the middle 50 vw of the screen. Pinned in Task 12.

## App checks (keyboard, controller, virtual monitor)

Unit tests don't prove the screen looks right or that it can still be driven without a mouse, so
the plan has **checkpoints** after the tasks that change something visible or focusable. The
session coordinating the work runs them itself (they need the user's trainer and Zwift Play, and the
guide page is the only channel to the user). Fix what a checkpoint finds before starting the next
task.

**Procedure** (workspace `CLAUDE.md`, "E2E testing with the real controllers"):
1. `rdctl start --virtual`, `rdctl move 2688 540`; `cd desktop && setsid -f sh -c 'npm run dev:local -- --remote-debugging-port=9223 > <log> 2>&1'`
   (full build the first time after a services or web-ui change; `--skip-build` only when nothing changed since).
2. Guide page: `python3 e2e/guide/server.py <log>` (http://localhost:8766, already known to the user); `e2e/inboxwait.sh` in the background and answer every message.
3. **Keyboard pass (no user needed):** click into the game (`rdctl click 2688 40`), drive it with real key presses through desktop control (controlling-linux-desktop skill: arrows, Enter, Escape). After each press read the focus with `node e2e/cdp.mjs "$(cat e2e/cands.js)"` (the `[FOCUS]` marker) and check: the focus ring is visible on the element, every interactive element of the screen is reachable, Enter activates, Escape goes back (during a ride: opens the pause menu).
4. **Screenshots:** `Page.captureScreenshot` over CDP (as in `e2e/cdp.mjs`); compare against the spec images; post them on the guide page for the user.
5. **Controller pass (with the user, only where a checkpoint says so):** `POST /state` on the guide page with the one button to press next (hotspot ids `l-up/down/left/right`, `r-a`, `r-b`, …), or `node e2e/coach.mjs` where its flows fit; ask the user to wake the controllers (Z logo) if they are off.
6. Poll for completion with a crash check (`grep "exited with signal" <log>`), never wait blindly. Close the game, `rdctl stop` and the mirror as soon as the checkpoint is done.
